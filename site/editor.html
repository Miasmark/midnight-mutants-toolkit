The cartridge editor

A manual for the tool that edits the game itself — rooms, terrain, sprites, palettes, text, music, and the rules underneath them — and writes a cartridge you can run.

Starting it

Nothing to install beyond Python. The interface is plain HTML and JavaScript served from your own machine — no framework, no build step, no network.

python tools/editor.py "Midnight Mutants (NTSC) (Atari) (1990).a78"
   -> http://127.0.0.1:7800

Disassemble sits beside Save. It runs the project's own disassembler over the edited image — unsaved changes included — and writes nine listings next to the cartridge, in under a second. The annotations describe the stock layout, so code added through the editor comes out as .byte rather than instructions.

On Windows, Edit Cartridge.bat and Edit PAL Cartridge.bat do the same thing by double-click. Either accepts a test-build name or a path.

It does not need the disassembly. Every table, header and pointer is resolved from the cartridge at load, so the listings, the annotations and the rebuild are no part of running it — a copy holding nothing but the tools and a .a78 works completely. Two optional files in build/ add names rather than function: without them rooms read "Unassigned" and sprite cells show offsets instead of identifications.

Before you begin

The cartridge you open is never written to. Everything happens to a copy in memory, and Save always asks where to put the result. The flip side: closing the window discards unsaved edits, because nothing is written until you ask.

The header

Four things sit along the top, and they answer the questions you ask most often.

whatit tells you
filenamewhich cartridge is loaded
NTSC / PAL which release the editor detected. Orange for NTSC, blue for PAL. It decides where every address lands, so it is worth a glance before you start.
bytes changed how far the image in memory has drifted from the file on disk. Zero means you have changed nothing.
Save / Revert write the result somewhere new, or throw the changes away. Both are disabled while nothing has changed.

The byte count is the honest measure of an edit. Moving an item is three bytes; repairing the debug cheat is four; recolouring a palette is one. If a change you thought was small reports hundreds, something larger happened than you intended.

The panels

Eleven tabs down the right-hand side. The room picture in the middle stays put; the panels change what you are editing about it.

Tiles

The area bank's character set, as a picker. Choose a tile here, then paint with it on the room. Characters are two bytes wide, so only even numbers are real tiles — the picker shows the 128 that exist.

Room

The room's own header: which graphics bank and character set it draws from, whether it is dark, which palette block it uses, and the terrain slice each scroll segment points at. Also how many segments it has — the room's width — and the map limit that decides where it ends. The canvas above will overlay collision, water and exits on request — the last labelling every scripted tile with where it leads, resolving the three events that defer to the room's own tables.

Also the terrain properties — what each tile does, as opposed to how it looks. Bits 0–1 are the collision class: 3 blocks everywhere, 1 and 2 block one half of the cell diagonal, 0 is open ground. Bit 7 makes the square scripted instead: a door, the healing well, the hurting ground, the win.

Exits

Where the room leads. North and south are per scroll segment; east and west are one destination each for the whole room. A destination of $00 means that edge is a wall.

Below them, the scripted doors and the conditions on them — the crypt key must be selected, not merely carried; one door wants the Ram beaten, a weapon in hand and nothing selected. Plus the doors that live in the terrain rather than at an edge, listed with what they demand of you and where they come out.

Actors

Six placement budgets per room — crow, bat, wolf, ghost, spider and the special actor — each one byte holding an amount and a rate mask. The mask is the reciprocal of the rate: $00 fires every frame, $FF is rare.

Then the global tables: how tough each creature kind is, the contact damage and stun constants, and the throw rate.

Items

Every instruction in the cartridge that names an inventory slot — twenty-nine of them — grouped by the item they name, so you can point any effect at a different item. The health ceiling, the weapon fire rates, what a new game starts with, the cost in blood purity of every kind of hit, and the repairs described further down.

Bosses

Each fight's setup record: health, contact damage, palette set, the player's starting position, and the stage counter that decides how angry the fight begins. Plus what winning is worth, the four bytes that are the weak spot, Dr Evil's two alternating windows, and the portraits themselves — which, since a fight draws no arena, are the whole of a boss's appearance.

The portraits are painted, not typed. Each is drawn from its own character set and palette with a cell grid over it, beside a tray of every character in that set: pick one, then click or drag on the picture; right-click erases. Colour follows the destination band rather than the portrait row, so Dr Evil — ten rows tall — changes colour down his length, exactly as the blit makes him.

Text

All 114 script records, searchable. Grampa's advice, the endings, the message screen, the status bar. Each record also carries two bytes worth editing: how long the banner holds, and whether its text shimmers.

Music

Songs, their two voice tracks, the patterns underneath and the individual notes — with a rendered preview of the edited image rather than the original. Below it, sound effects: the 17 sites that ask for one, listed by what fires them, and all 15 streams in the block with which ids play each. Three of those streams nothing plays at all.

Draw

Pixel editing, for both kinds of artwork: the room's character set, and the sprite pages holding the player, the creatures, the item icons and Grampa. A pixel is two bits, so it is transparent or one of three colours — and which three depends on where it is drawn.

Colour

Every palette block in the cartridge, against the whole 7800 space: sixteen hues across, sixteen luminances down. The terrain block, the sprite block that is live during play, the intro block and the three boss sets.

Changes

Every byte that differs from the file on disk, as rom+offset from → to. Patch files are written and read from here.

What is shared

The single most useful thing to know about this cartridge: very little of it belongs to one room.

128K is not much for a game this size, and the authors reused everything. A change that looks local usually is not, so each panel says who else it affects before you commit.

editing thisalso changes
a terrain tile every room drawing that slice — 17 rooms share b1 slice $2A
a character every room in that bank with the same character set — up to 19
a terrain property the other rooms on that property table, and the paired character, since two share one entry
a room palette every room with the same stream — up to 11
a sprite everywhere it appears; sprite pages are global
a creature's toughness every room that places that kind
an item icon palette the six other items sharing it

Where a room needs to differ alone, the lever is usually to point it at different shared data rather than to edit what it currently uses — give the segment another terrain slice, or the room another palette stream.

What it refuses

The ROM is a fixed 128K with no slack, so the editor writes in place and declines anything that would move data.

  • Nothing may change size. A terrain slice is exactly 200 bytes. Replacement text may be shorter but never longer, and is padded rather than shifted. A pattern's note count is fixed.
  • Structural fields are not editable. A room's segment count sets the length of five parallel arrays that follow it; changing it would run into the next room's header.
  • Code edits are anchored. Every constant that lives inside an instruction records the opcode that must precede it. If that opcode is not there, the write is refused rather than scribbling into code that has moved.
  • Save is blocked if any of the 76 rooms stops parsing, so a bad header edit cannot reach a file.
  • Unknown cartridges are refused outright rather than edited blind.

Values are bounded too: a pixel is two bits, a pitch is five, a colour slot is 1–3 because 0 is transparent, and a boss is 1–3 because slot 0 is a null pointer.

Patch files

Share an edit as the handful of bytes that changed, rather than as a 128K cartridge.

The Changes tab writes and reads BPS patches. Eight changed bytes come out as an 82-byte file. The format is the one Floating IPS, RomPatcher.js and beat all speak, so a patch from here works with them and theirs works here.

Why BPS and not IPS

formatverifies
IPSnothing — offsets and data only. Applied to the wrong ROM it corrupts it silently.
UPSCRC32 of source, target and patch; less widely supported now.
BPSCRC32 of source, target and the patch itself — and it is what current tools default to.

All three checksums are used: the patch's own on load, so a corrupt file is caught before it touches anything; the source checksum before applying, with both values shown if they disagree; and the result afterwards.

Worth knowing

Loading a patch applies it over the cartridge as it is on disk, replacing unsaved edits. That keeps every patch relative to the stock image — otherwise two patches applied in sequence would describe something neither of them says.

Both releases

The European cartridge is the same game at different addresses, and the editor handles it without you doing anything.

Its display list carries extra zones for PAL's taller screen, and those insertions push the code after them along: bank 6 by three bytes, part of bank 7 by nine. The editor identifies the cartridge on load, relocates its address tables to match, and shows the result on the badge. Every panel then works identically.

Addresses shown in the interface are the loaded image's own, so they line up with that version's listings. The full comparison — what moved, what did not, and what actually differs between the two — is on its own page.

The repairs

Nine things in the cartridge are broken, or missing, in ways the editor can put right. Every one is a toggle, and every one reverts byte-exactly.

The debug cheat that reboots your console

Holding PAUSE and pressing the first button four times was meant to refill blood purity and grant eight maximum health. It can never get there: two of the four counter states branch into data, and so do both wrong-button exits. Since the IRQ vector is the reset entry, each is a soft reboot — the counter can be advanced exactly once before the game restarts.

The repair is four branch operands and nothing else. No instruction moves.

Music that runs a sixth too slow

A note's duration is a count of frames and the engine ticks once per frame, so tempo follows the machine. The European release was never retimed — its duration table is byte-identical to the NTSC one — so at 49.92 Hz against 59.96 everything plays at 83.3% speed.

Two fixes. Rescaling multiplies the sixteen duration entries by 5/6: data only, but eight of them round, and the melody's clean 2:1 becomes 13:7. The extra tick installs an 16-byte shim on the music entry vector that runs one extra tick every fifth frame — 18 bytes in all, counting the two that repoint the vector at it. 0.1% out, every note ratio preserved, and confirmed by ear on the PAL machine.

A targeting bracket for a leg

The last frame of a special actor's death draws four eight-pixel fragments, and the fourth names gfx $EE — the same eight pixels the Grampa screen uses for its item-select reticle. A bracket appears briefly as the corpse's right leg.

The artwork has no fourth fragment to reach for: $EC and $EE are the two halves of one sixteen-pixel cell, and the right half is the reticle. The repair points the fourth fragment at $EC as well, so the corpse gets two of the same melt piece. One byte, and nothing moves — only which eight pixels are fetched.

Three items you cannot see when you select them

The status bar draws whatever is selected from two tables indexed by the selected slot: graphics at f6:$6838, palette and width at f6:$6845. The cartridge carries a second, correct copy of the same information for items lying on the ground, and putting them side by side is the whole diagnosis.

itemon the ground in the status bar
crypt key$D6 / $9E $D6 / $BE
necklace$D2 / $9E $D2 / $BE
plasmic pumpkin$F4 / $DE $D0 / $BE

That zone loads its palettes from dat_4D1B, which makes palette 5 $00 $11 $14 — its first colour is pure black — and palette 4 $1A $22 $0D, a light gold. Every lit pixel of the crypt key is that first colour, so it renders as nothing at all. The necklace is mostly that colour with a little $11, which is why it reads as a smudge rather than a necklace. The weapons in the same tables already use palette 4 and are perfectly legible.

The pumpkin is wrong twice. Its graphics entry is a copy of the heart's $D0. And on the ground it uses palette 6, which the game randomises every frame — the pumpkin and the diamond are the only two items on it, which is why those two sparkle where nothing else does. The status strip holds its palettes fixed for the whole zone and cannot do that, so even with the right artwork it stays a dim brown outline until it is moved to palette 4 as well.

Four bytes. The crypt key becomes a gold key where there was nothing, the necklace a beaded ring, and the pumpkin its own lit artwork.

The item that never says anything

Every item announces itself when you pick it up — except the plasmic pumpkin. The chain at f6:$527A links kind 1 to the cross's line, 2 to the crypt key's, 3 to the necklace's, 4 to the heart's, 9 to the lantern's, and falls straight through to an RTS for kind 5. It is not a broken pointer or a record that went missing; the case was never written.

That silence costs the player something real. The pumpkin is what ends the game: carrying it selected onto the square whose terrain property is $EF wins, and exactly one room places that square — room $1A, in the pumpkin fields. Nothing in the shipped game says so.

The pointer table has room for the fix already. Five of its 73 entries — $24 $25 $26 $27 and $32 — have no code path that can produce them, each idly aimed at a neighbour's record. Slot $24 can be pointed at a new record without growing anything or stranding anything.

The record ends $FE, not $FF. That single byte is what makes the banner shimmer. sub_687E scans to the byte that ends the text and, if it is $FE, puts $FF in ram_1E7B; the display interrupt then runs LDA ram_0044 / AND ram_1E7B / STA P0C2, so the frame counter walks the text colour one step per frame. With $FF the mask is zero and the words sit still. Nearly every stock pickup ends $FE — but four do not, and the editor offers the flip as a repair.

The four pickups that never shimmer

Walking all 73 records and reading the byte each one stops on turns up four exceptions, and every one of them is a pickup.

The knife's own four lines shimmer, as do both potions, the crypt key, necklace, heart, lantern and all four diamond variants. There is no rule under which the knife shimmers and the axe does not, which is what makes these four look like an oversight rather than a distinction. Four bytes.

The line itself is editable: up to 48 characters, with | breaking it and no single line over 39, the widest the display fits. The default reads TAKE IT TO THE PUMPKIN FIELDS / AND SET ME FREE!

Widening a room moves its header

An area header is 25 + 5n bytes: 24 scalars, a $00-terminated list of n terrain-slice ids, then four parallel n-entry exit arrays. The segment count is the room's width, so changing it resizes the record.

They cannot grow where they sit. The shipped headers are packed with nothing to spare, and five of them overlap their neighbour — room $10's header begins three bytes inside room $0F's last exit array, so its stream, page and dark flag are the tail of the room before it. Editing a tail in place would silently rewrite the next room.

So the editor moves the record instead. Headers are reached through the pointer table at f7:$F32A and never by walking, so one may live anywhere; relocating leaves the original bytes untouched, which is exactly what the overlapping rooms need. Coming back to the shipped count writes the record home again, edits included, and releases the borrowed space.

Five segments is the ceiling, and it is the engine's rather than the editor's. The map builder at f7:$F243 lays each segment 20 columns into a 100×10 buffer at $2400, so five fill it exactly; a sixth would start at column 100 — the second band — and its last row would run past $27E7 over score_digits. Fourteen shipped rooms already use five and three use four, so there is nothing unusual about going past three.

Space is not the binding constraint. A header must sit at $F3CA or above to stay a room to the rest of the toolchain, which leaves 86 bytes at $FF24 and 30 at $FEE2; a five-segment header is 50 bytes, so the larger run takes anything the engine allows.

Gated deliberately

Both music corrections are refused on an NTSC cartridge, in the interface and in the server alike: applying either to a 60 Hz machine makes the music run 20% fast. Turning them off stays available on any image, so a wrongly patched cartridge can always be put back.
