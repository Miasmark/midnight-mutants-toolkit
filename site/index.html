Cartridge

Three windows onto eight banks

The .a78 header claims SuperGame with bank 6 at $4000. That was confirmed rather than trusted: RESET ends in JMP $4000, and $4000 holds a valid jump table — only true under this mapping.

The engine. Vector table, DLI handlers, main loop, item and terrain logic.

$8000–$BFFF
paged · bank 0–7

The window. Area graphics, the script, and three separate code banks.

$C000–$FFFF

Sprites, the service jump table, area descriptors, RESET and the vectors.

permanently mapped paged through $8000

Only banks 6 and 7 are always visible, so they carry the cross-bank ABI: two jump tables, five slots at $4000 and twenty-three at $D000. Every call between banks goes through them.

Paging is a write to anywhere in $8000-$FFFF, and the register cannot be read back, so the engine keeps a shadow copy in $BF:

    LDA  #$03
    STA  $8000     ; any write to $8000-$FFFF sets the bank
    STA  $BF       ; shadow it, because interrupts will clobber it
    JSR  $8000     ; ...and now $8000 is bank 3's code

Boot

The BIOS is gone by the second instruction

Worth knowing if you are wondering whether the console BIOS images matter for studying the game. They matter for the power-on handshake and nothing after it.

; bank 7, $FF00 -- RESET
    LDA  #$07
    STA  INPTCTRL   ; 7800 mode, MARIA enabled, BIOS ROM mapped out
    CLI
    CLD
    LDA  #$7F
    STA  CTRL       ; MARIA DMA off while we set up
    LDX  #$FF
    TXS
    LDA  #$00
    STA  $8000      ; select bank 0
    STA  $BF        ; shadow copy -- cur_bank
    STA  OFFSET
    LDX  #$40       ; clear zero page $40-$FF
    ;               ($00-$3F is TIA and MARIA, not RAM)
    JMP  $4000      ; into the engine via the bank-6 table

Display

Three interrupts, one of which does nothing

MARIA raises NMI at the end of any display-list zone flagged for it. The vector at $400C is JMP ($2135) — indirect through RAM — so every handler installs its own successor. The disassembler rediscovers the chain by scanning for the stores that write that vector.

$4104

Top of frame. Sets border and palette registers, then arms the sync tick.

$416F

DEC $1E68, then RTI. One instruction. Its only job is to happen.

$400F

Per-zone palette swap, eleven zones, four bytes each from $1ECC.

Why a do-nothing interrupt earns its slot

Foreground code cannot page a bank out while MARIA is still reading graphics from it, and there is no status bit to poll. So the engine parks the CPU against the raster instead:

    LDA  $BF        ; hold the bank we want back
L_4152:
    BIT  $1E68
    BEQ  L_4152     ; spin until the $416F tick fires
    STA  $8000      ; safe now -- the raster has passed the zone

MARIA runs with CTRL = $50: DMA on, one-byte characters, read mode 00 (160×2). The display list list sits at $0140 in RAM.

Graphics

Character sets stored sideways

In character-map mode MARIA builds a glyph's address as ((CHARBASE + line) << 8) | char_number. The line number lands in the high byte, so a character set is line-planar: one whole 256-byte page holds line 0 of every character, the next holds line 1. At 160×2 each byte is four 2-bit pixels, so a character is four pixels wide.

Rendered as four grey levels, one per 2-bit pixel value. Deliberate: the colours are not in the ROM at these addresses — they are written to MARIA's palette registers at run time and swapped per zone by the DLI. The startup palette is a 24-byte table at $4D1B copied into $28–$3F, skipping every fourth register because those slots are control registers, not colours. All 11 sheets are in build/gfx/.

Map

The level you see and the level you walk into are the same stream

The world is 160×800 units, wrapped into a 10×100 grid — one cell per 16 units of X and 8 of Y. The grid lives in RAM as ten 100-byte column strips based at $2400, $2464, $24C8 and so on, addressed through a pair of tables at $D281.

MapTileAt, slot 9 of the bank-7 service table, resolves a position in three steps:

; in:  Y = world X, X = world Y low, A = world Y high
; out: A = terrain code, 0 when out of bounds

    strip   = tbl_MapStrip[worldX >> 4]
    cell    = strip[worldY >> 3]
    terrain = area_ptr[cell >> 1]

So the grid does not hold terrain directly — it holds an index, doubled, into a per-area property table that area_ptr points at in bank 7. Change the area, and the same grid byte means something else. World X above $A0 wraps by subtracting $10 and adding 7 to Y.

The area builder

BuildArea at b3:$8000 unpacks an area from a record stream, five bytes at a time: $80 means the next two bytes are a new source pointer to follow, $FF ends the stream, and any other lead byte is the row the record belongs to — it is skipped unless that row is the one being built.

The builder runs twice, and $90 selects which of two parallel structures it fills:

passlist datapointer table
0$2200$1800
1$2400$1B00

Each row's slot in those pointer tables comes from a small offset table, and the offsets step by three — MARIA display-list-list entry size. So both passes build display structures.

Double buffering

FlipDisplayBuffer at b3:$8276 waits on MSTAT for the end of the visible field, points DPPH at $18 or $1B, and toggles build_pass so the next build fills whichever buffer is now off-screen. Both display list lists are seeded from a template and both are genuinely handed to MARIA.

Resolved: the character map is the terrain grid

Settled by running the cartridge in MAME and dumping memory. The live display list at $2200 holds MARIA 5-byte headers whose data pointers are exactly the strip bases, with the indirect (character map) bit set in byte 1:

  00 60 24 2B 00   data $2400, indirect, write mode 1, palette 1, width 21
  64 60 24 0B 00   data $2464, indirect, write mode 1, palette 0, width 21
  C8 60 24 2B 00   data $24C8, ...

And the live bytes at $2400 are all even and all below $80 — exactly the doubled indices MapTileAt expects.

So one set of bytes does both jobs. Each byte is the character number MARIA draws for that cell, and byte >> 1 is the index into the per-area terrain table that decides whether you can walk there. There was never a separate map, and the two addressing schemes were never in conflict — the display list points at the grid in indirect mode, which is the piece I had missed through three attempts at explaining it.

The five visible entries all sit at hpos $00 with width 21, stacked vertically, so a strip is a horizontal band 100 cells long with 21 on screen. That also means the axes were labelled backwards: the 16-bit coordinate is the long scrolling axis and the single byte is the short one.

Script

Plain ASCII, hiding in plain sight

The dialogue is not compressed or re-encoded. It is uppercase ASCII, which is why the tracer kept walking into it and decoding $52 as JAM. Those bogus opcodes were the tell — 113 records, forty-three in bank 0 and five in the engine bank near $6BBF. A second, unframed pool of monster taunts sits at $BC26.

    $FF <p1> <p2> '@'  record header, then the text, then  '#'

    $40 @  start of text        $7C |  newline  (dst += $16 -- 22 columns)
    $23 #  end of text          $26 &  new page (reset column, then newline)
    $5E ^  apostrophe            $2A *  draw glyph $3C

  p1 -> text palette      p2 -> index into the indent table at $A4B2

The 22-column figure is not a guess: the newline routine at $A2C6 adds $16 to the destination pointer. All 113 records are decoded in TEXT.md, including Grampa's hints, which together amount to a walkthrough.

Mechanics

Player state

Four bytes carry almost everything. RAM_MAP.md lists all 417 referenced addresses; these are the ones that drive the game.

Terrain

TerrainDispatch at $5776 switches on the code under the player. $A0 is the healing well: it adds a single point per tick, clamped to hp_max, and never writes hp_max — which is why it refills the bar but never extends it. Only diamonds and the bank-5 sequence reward do that. $EF is the final target, $8C, $8E and $8F are further handlers, and anything ≥ $F0 goes to $5810.

Tracing one line of dialogue back to its condition

Grampa's line "SO YOU WANT TO BE RAISED FROM THE DEAD?" is slot $0F of a 50-entry pointer table. The selector takes the first match:

GrampaPickMessage:
    LDA  forced_msg     ; $1F9E -- a message forced by an event
    BNE  ...            ;   -> ($1F9E & $7F) | $20
    LDA  undead_flag    ; $1FD5 -- blood purity reached zero
    BNE  ...            ;   -> $0C  "YOU'RE ONE OF THE UNDEAD"
    LDA  win_flag       ; $1FCD
    BNE  ...            ;   -> $0D  the rescue ending
    LDA  death_state    ; $8B   -- you are dead
    BEQ  hints
    LDA  revive_ok      ; $1FD3 -- latched while you were alive
    BEQ  no_revive      ;   -> $0B  "HIT RESET TO RESTART"
    ...halve hp_max, hp_cur = hp_max, clear death_state...
    LDX  #$0F           ;   -> the resurrection

The latch happens in a tick every eighth frame, and only while blood purity is non-zero, the mode flag is clear, and maximum health is at least 48. Maximum health starts at 39, so early on Grampa cannot resurrect you at all. Diamonds raise the ceiling by 8 each; the resurrection then halves it again, so the mechanic pays for itself. Dying of blood poisoning takes a different branch entirely and can never be revived — which is what the line goes on to say about not being able to purify your blood.

And one thing left in by accident

A routine at $BDC2 runs only while the console PAUSE switch is held. It counts button presses and eventually grants bonus maximum health. It reads as abandoned debug code: the intermediate states branch to $BE0E and $BE13, which are both inside the sound-effect data, so the bonus cannot be reached without crashing first.

Darkness

The cave is not drawn differently — it is just never lit

Settled by replaying a recorded play session in MAME and sampling the zone palette shadow every 30 frames. FadeToBlack (b3:$85FC) ramps every zone palette down to $00, writing both the shadow and the live MARIA register, and every area transition runs it. A lit area then ramps back up over about 60 frames. The cave does not.

; entering a lit area (frames 9180-9240)
    00 00 00 00  ->  00 01 11 11  ->  00 02 13 11

; entering the cave without the lantern (frame 10560 onward)
    00 00 00 00  ->  00 00 00 00  ->  00 00 00 00   ...indefinitely

So there is no separate dark-rendering path. The character map, display lists and collision all keep running — the player moves normally and enemies still reach and kill them — but every colour register is black, so nothing reaches the screen. The cave is area type $09; type $08 areas ramp up as usual.

Still open: the routine that ramps the palette back up, and the lantern check that must gate it for type $09.

Enemies

Three damage models, and a weapon that does nothing

Every hit adds weapon_level to a counter, but the counter, the threshold and the meaning differ by target:

targetcounterdies atweapon level
ordinary actorsactor_mode$A0is the damage
special actorssactor_damage8-bit overflowis the damage
bossesboss_health0 (counts down)gate only

The knife is weapon level 0. It adds nothing anywhere, so it can only kill things already past their threshold — crows, bats, wolves and enemy projectiles. Against anything with health it registers the hit, plays the flash, and does zero. Against a boss it is refused outright.

Against bosses the weapon level is only a gate, so axe, blaster and mega blaster all remove exactly one point per hit. Measured over a recorded fight: 64 hits, one point each. The mega blaster is better solely because its cooldown is $0A against the axe's $1E.

The AI is twenty instructions

SetActorVelocity homes at the player on both axes, then a random two-bit value masks one axis to zero:

vel_long  = (pos_long  < target) ? +1 : -1
vel_cross = (pos_cross < target) ? +1 : -1
Y = Random & 3
vel_cross &= [$FF $FF $FF $00][Y]
vel_long  &= [$FF $FF $00 $FF][Y]

Half the time both axes survive and the enemy charges diagonally; a quarter it moves only across, a quarter only along. The direction is never away from the player, so the randomness chooses how directly an enemy converges, never whether it does. That is the whole shamble — no state machine, no pathfinding, and nothing to lose a pursuer with.

Unless you are carrying the cross

Which is where the cross comes in. It is normally described as a defensive item, and it is: contact blood loss is halved, or waived entirely while it is the selected item, and every source of health damage is halved. But four of its eight effects act on the enemies rather than on the player, and one of them reaches into the routine above.

The homing target is not read directly. A short preamble sets it to the player's position, then checks the inventory — and if the cross is held, three times in four it overwrites that target with a random point on the map:

    LDA  itm_cross
    BEQ  SetActorVelocity    ; no cross -> target stays the player
    JSR  Random / AND #$03
    BEQ  SetActorVelocity    ; 1 in 4 -> still the player
    JSR  Random / AND #$3F / ADC #$20 / STA target_cross
    JSR  Random / AND #$7F / ADC #$14 / STA target_long

The AI underneath is untouched — it still converges on its target as relentlessly as ever. The cross simply lies to it about where you are. So the same code that cannot be shaken produces a room full of wandering enemies, and the one update in four that does target you is what keeps them from being harmless.

Spawning is throttled too. An area's actor definition byte packs an amount in the high nibble and a rate mask in the low one. Areas that carry the marker $EF resolve it by inventory: $FF without the cross, which is unbounded and spawns every frame, and $22 with it — at most two, one chance in 64. Counted on the machine, three rooms that hold eight live actors hold none with the cross. The effect is authored per area, so only rooms carrying the marker respond at all.

One path is exempt: an actor's velocity at the moment it spawns is set without the inventory check, so everything launches straight at you and can only be scattered afterwards.

Bosses

Three hand-written fights, and no arena

A boss fight loads no room. BossSetup reads a 32-byte record and blits a single large picture straight into the character map at $2400 — and the picture is the boss itself. That is why the area loader is bypassed and why the room map has 76 entries and no arenas: there is nothing to describe but a portrait and the fight running over it.

bossroomhealthtouchportrait
Skull$1E64109×9 chars
Ram$1540516×9
Dr Evil$3C1609 + purity20×10

They escalate. A stage counter climbs one step roughly every 17 seconds and indexes a mask; the attack fires only when Random AND mask is zero, so the mask is the reciprocal of the rate. It starts at one shot in 64 and reaches $00 — every frame. Being hit advances the index by five while the flash is on, so striking a boss makes it retaliate harder.

Dr Evil alternates his weak spot. Bit 7 of a frame counter picks one of two ten-unit windows 56 apart, and only the exposed one can be damaged. The same flag places his shot, so the projectile always leaves the ear you can currently hit. Rendered, the two windows land exactly on the pointed ears of his portrait.

All three move on dat_DD00, the same sine table that drives the zombie head bob and the flying actors' drift.

Player

Two bars, and two ways to lose

Health and blood purity start at 39 and 100. They have independent consumers and either reaching zero kills you, but the two deaths are not the same.

Blood is terminal. Purity at zero sets undead_flag and ends the run; there is no resurrection from it. Health can be survived — but only if hp_max has reached $30, and the diamond is the only thing that raises it, by 8 from a base of $27.

diamondshp_maxrevivable

So the diamond is not a health pickup at all — nothing ever reads its inventory slot. It is the gate on a second life, and it takes two.

The cross changes what you become. Dying of blood loss sets undead_flag to $FF holding the cross and $FE without. Same message, same finality — but without it the player's sprite is drawn from the creature page using the bat's own cells. Drained of blood, you become the thing that drained you.

Sound

Two engines, one channel each

Effects are a byte-stream interpreter in bank 0 driving channel 0. Music is a separate two-voice tracker in the fixed bank with its own five-stage ADSR. It addresses TIA indexed by voice — STA AUDF0,X — so it never names AUDF1 and does not appear in a search for it.

Data is three levels deep: a song table of track pointers, tracks of pattern pointers, patterns of two-byte notes. A track's terminator says whether to loop, stop, or chain to another song — the main theme is two songs chained to each other, so it never ends.

One byte carries both timbre and pitch. AUDF is a five-bit register; the player writes the whole byte and the chip keeps the low five, then shifts the same byte right by five and uses the three bits the chip discarded to pick the waveform.

The area's graphics page picks its music. The byte that selects a room's artwork indexes the song table too, so rooms that look alike sound alike. Death is modelled as entering an area: the dirge is simply the tune of area type $0A.

Maps

Terrain is a table copy, and it regenerates offline

The grid at $2400 is not built from the area record stream. The real writer is f7:$F243, a plain copy out of the paged area bank — the room is assembled from pre-drawn 200-byte slices, ten bands of twenty, selected per scroll segment.

n   = $1EC6                 slice count, from the area header
sel = $1EC7 + x             per-slice source selector
src = tbl_F2B4[sel] | tbl_F2E8[sel] << 8
dst = $2400 + tbl_F31D[x]

for slice x < n:
    for band in 0..9:
        copy 20 bytes src -> dst
        src += $14 ; dst += $64

Reproducing that offline regenerates any room from the cartridge with no emulator involved. Resolving the area header for the character set, the paged bank and the palette block on top of it renders all 76 rooms in colour — every room picture in this teardown is drawn from ROM, not captured.

That also measures the area banks. The $8000-$BFFF window holds two 128-character sets and 39 terrain slices: 15,992 of 16,384 bytes claimed by known readers, the remainder a slice of zeroes.

How rooms connect

Rooms have real exits, and they live in the area header. North and south are per scroll segment; east and west are one destination for the whole room. Each vertical edge takes two arrays — a destination and the arrival point — which is why the header holds five arrays, not four.

edgeheaderread attaken when
northarrays 2 + 3f6:$57E2cross position drops below $0A
southarrays 4 + 5f6:$57F9cross position reaches $A0
west+5f6:$591Eworld position falls below $1D
east+6f6:$5935world position reaches map_limit

A destination of $00 means that edge is a wall. The two vertical tables are told apart by where they drop you: north arrivals set the bottom of the new room, south arrivals the top.

East and west are how the caves and the woods thread together — 43 rooms have one. Four of them, $2C, $2D, $31 and $38, name themselves on both sides, so walking either way returns you where you started. Nothing else in the exit data does that.

The other connections are scripted terrain: cells with bit 7 set are doors and warps rather than ground, and the three boss doors are gated on boss_flags, so a door stops working once its boss is dead.

Credits

Who made it, per the ROM itself

A credits run sits at f6:$73F7, shown across the screens before the final boss. It uses a second text framing — <$FE|$FF> <p1> <p2> then text, running to the next $FE/$FF, with no @ introducer and no # terminator. That is why the first extraction pass, which looked only for the Grampa message shape, missed it entirely.

Debug hook

A cheat that resets your console instead

DbgPauseHook at b0:$BDC2 is called from $A31F only while the console PAUSE switch is held. It reads the controller buttons directly — bit 7 set means pressed, confirmed against how the game polls them in normal play — and steps a counter, dbg_step ($1FDC).

DbgPauseHook:
    LDA  dbg_step
    BEQ  read_buttons     ; step 0 -> read
    CMP  #$01 / BEQ $BDFA ; step 1 -> broken path
    CMP  #$02 / BEQ $BDFA ; step 2 -> broken path
    CMP  #$03 / BEQ read_buttons
    LDA #$64 / STA blood_purity    ; step >= 4: the payout
    LDA hp_max / ADC #$08 / STA hp_max / STA hp_cur
    LDA  #$00 / STA dbg_step

read_buttons:
    LDA  INPT0 / ORA INPT2 / ORA INPT3
    BMI  $BE0E            ; any other button held -> sound data
    LDA  INPT1
    BPL  $BE13            ; INPT1 not held -> sound data
    INC  dbg_step
    LDA  INPT1 / BMI *-2  ; debounce: wait for release
    RTS

So the intended input is narrow: hold PAUSE, hold INPT1 alone, with the other three button lines released. Each clean press advances the counter by one, and at four it grants +8 maximum health and refills blood purity to 100.

It can never get there. Steps 0 and 3 reach the button reader, but steps 1 and 2 branch unconditionally to $BDFA, which falls off the end of the routine into $BE00. That address is sound-effect data, and so are the two wrong-button targets $BE0E and $BE13. All three reach a BRK within a few bytes:

  BE00: 08        PHP
  BE01: BE FF 00  LDX $00FF,Y
  BE04: 4D BE FF  EOR $FFBE
  BE07: 00        BRK        ; IRQ vector is $FF00 -- the reset entry

Because the IRQ vector points at RESET, the failure mode is a soft reset rather than a hang. The counter can be advanced exactly once before the next invocation reboots the game, so the bonus is unreachable in any build of the ROM as shipped.

Toolchain

34 tools, and why one of them is an assembler

A disassembler alone produces something plausible. Pairing it with an assembler that speaks the same dialect turns the output into a claim that can fail: reassemble, compare, and any mistake in instruction decoding or code/data classification shows up immediately as a mismatch.

It has already earned its keep — the round trip caught a stale bank in the tracer, a label swallowed by a data block, and a call being attributed to the wrong bank entirely.

And an emulator, for when reading stalls

Some questions are cheaper to observe than to derive. tools/mame/ drives the cartridge headless in MAME at about 4500% speed, so a 45-second in-game run costs roughly a second. watch.lua samples all of RAM at chosen frames, which finds timers and slow state by diffing rather than by reading code.

This is what finally settled the character-map question after three failed static explanations, and it independently confirmed both the bank mapping and the zero-page RAM mirroring. One caveat worth recording: MARIA's registers are write-only, so dumping DPPH or CTRL from Lua tells you nothing.

Method

How much of this is actually known

The listings reassemble into a byte-identical cartridge, so instruction decoding and the code/data split are not in question. The interpretation on top of that varies, and the reference marks which is which. Three kinds of statement are kept apart throughout, and the distinction is load-bearing: traced, read from instructions with the address given; measured, observed on a running machine with the method given; observed, taken from play and marked as such.

  • Proven. Banking and boot, the DLI chain, the text format and the character-set layout, all 76 rooms and their four kinds of exit, the doors and their gates, every inventory slot and what reads it, actor spawning and the damage rules, the bosses, the player's two bars and both endings, and the sound engine with all eleven songs — each read off code that rebuilds.
  • Assumed, and recorded as such. A handful of bank-switch sites where the bank comes from a table or a shadow variable, pinned by hand in annotations.json under banksw and bankat.
  • Guessed. Content labels in the page-level memory map for regions the tracer never reached — the classifier calls some data "CODE?" and it is wrong about it.

Traced-as-code coverage is 54.2% of the engine bank and 11.0% of the cartridge. That is not a gap: the rest is tables and artwork. The largest block of it is now measured rather than assumed — an area bank's window is 98% claimed by two known readers.

Still open

Nothing structural. What remains is soft. All seven referenced instruments are characterised by role, range, note length and waveform and each is rendered playing its own notes, but nobody has sat with the audio and named the timbres; whether the nine unused instrument rows are abandoned drafts or an unused library is not something the data settles. Two hitbox marks on the boss page are placed from play rather than derived, because a portrait narrower than the screen leaves its window origin underdetermined. And three sites pass a song number in a register that is not traced to a constant, though all three are accounted for by the area-type mechanism.

The rebuild is byte-identical to the cartridge, which bounds all of it: no claim here can be hiding a misread instruction, only a misread intention.
